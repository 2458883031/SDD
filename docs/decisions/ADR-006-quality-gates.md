# ADR-006：质量门禁与人工审批

**状态：** 已采纳  
**日期：** 2026-11-20

## 背景

软件研发的关键节点需要人工确认，防止 AI 擅自做出不可逆决策。

## 问题

如何设计质量门禁：
- 既保证质量又不阻碍效率
- 明确哪些必须人工审批
- 支持自动化检查 + 人工确认的组合

## 候选方案

### 方案 A：全自动执行

不设门禁，AI 自主完成所有步骤。

**优点：** 速度最快  
**缺点：** 风险高，不可逆错误难恢复

### 方案 B：全人工审批

每个步骤都等待人工确认。

**优点：** 控制力强  
**缺点：** 效率极低，不符合快速迭代需求

### 方案 C：分级门禁（选定）

根据任务类型和复杂度，设置不同级别的人工介入。

**优点：**
- 简单任务快速执行
- 复杂任务关键节点把关
- 平衡效率与质量

**缺点：**
- 需要定义分级规则
- 边界情况可能判断失误

## 决策

采用**方案 C：分级门禁**。本 ADR 是 G1–G6 的**唯一权威定义**；其他文档引用本 ADR，不重复定义门禁规则。

### 1. 门禁总览

| 门禁 | 名称 | 核心控制内容 |
|------|------|--------------|
| G1 | 需求确认 | 需求范围、目标、约束、验收标准 |
| G2 | 设计确认 | 技术方案、架构影响、设计风险 |
| G3 | 开发计划 | 任务拆解、依赖关系、资源与实施顺序 |
| G4 | 代码质量 | 代码规范、静态检查、独立 Code Review |
| G5 | 测试验收 | 测试结果、验收标准、回归风险 |
| G6 | 部署授权 | 部署目标、环境风险、变更授权 |

### 2. 通用原则

1. **自动检查与人工审批分离**：自动检查可以始终执行；人工审批只在规则要求时触发。
2. **不是所有门禁都需要人工审批**：低风险任务可以简化，但不得跳过安全约束。
3. **超时/沉默不等于批准**：审批必须有显式决定。
4. **严重风险不得自批**：Agent 不能批准自己的高风险操作。
5. **审批记录可追溯**：每次门禁记录检查项、结果、审批人、时间和依据。
6. **失败必须回退**：门禁失败不得直接进入下一阶段。
7. **Review 与 Testing 独立**：测试通过不代表 Review 通过，Review 通过也不代表测试通过。

### 3. G1：需求确认

- **触发**：任务进入 requirements 节点；L2/L3 默认触发，L1 可简化。
- **自动检查**：需求文档存在；`goal/scope/constraints/acceptance_criteria/non_goals` 完整；歧义清单；外部依赖与安全影响标记。
- **人工审批**：L2/L3；安全敏感；新增外部依赖；需求范围不清晰；用户明确要求。
- **允许跳过**：L1 且范围明确、无安全/外部依赖、用户明确同意简化；记录简化理由。
- **不允许跳过**：安全敏感、新增外部依赖、需求歧义、用户明确要求审批。
- **失败回退**：返回 requirements-clarity；不得进入 analysis/design。
- **通过状态**：`requirements_approved`；`current-stage` 进入 analysis/design。
- **审计**：检查清单、审批人、时间、决定、简化理由。

### 4. G2：设计确认

- **触发**：design 节点完成；L2/L3；安全敏感任务。
- **自动检查**：设计文档；架构影响；接口/数据模型；安全考虑；备选方案；可测试性；回滚/迁移方案。
- **人工审批**：L3；跨模块；安全敏感；新增依赖或外部服务；用户要求。
- **允许跳过**：L1 局部修改，且无接口、数据模型、安全或外部依赖变化。
- **不允许跳过**：新服务/新模块、数据模型变更、认证/授权/加密、外部 API、生产架构变更。
- **失败回退**：返回 design；如方案不可行，回退 analysis 或 requirements。
- **通过状态**：`design_approved`。
- **审计**：Builder Check 结果 + 人工审批记录。

### 5. G3：开发计划

- **触发**：coding 之前的计划节点；L2/L3。
- **自动检查**：任务拆解；依赖关系；负责人；实施顺序；风险；回滚/验证计划。
- **人工审批**：L3；多 Agent/并行执行；跨团队依赖；高风险变更。
- **允许跳过**：L1/L2 且计划清晰、无跨团队/高风险依赖。
- **不允许跳过**：多 Agent 并行、跨团队依赖、高风险变更。
- **失败回退**：重新制定计划；不得开始 coding。
- **通过状态**：`plan_approved`。
- **审计**：计划版本、审批人、时间。

### 6. G4：代码质量

- **触发**：有代码变更；code-review 节点。
- **自动检查**：lint/格式/类型/静态分析；变更相关的聚焦测试；密钥扫描；依赖安全检查；diff 审查。
- **人工/独立审查**：所有代码变更必须有独立 Review。L1 可以由独立 Agent 或自动化 Reviewer 完成聚焦 diff 审查，但作者自审不算独立 Review；必须记录审查证据。
- **允许跳过**：仅文档变更（无代码）时 G4 记为 N/A。
- **不允许跳过**：任何代码变更、安全敏感变更。
- **L1 说明**：L1 纯文档变更记 N/A；L1 代码变更必须执行简化 G4（由独立 Agent 或自动化 Reviewer 审查 diff），不得跳过。
- **失败回退**：严重问题（正确性/安全/数据丢失）返回 coding，禁止进入 quality gate；轻微问题修复后可继续，或记录为后续项并由用户接受，不得静默放过。
- **版本绑定**：G4 必须记录被审查的 commit 或产物 hash；Coding 产生新代码版本后，旧版本的 G4 结果失效，必须重新 Review。
- **通过状态**：`code_review_approved`。
- **审计**：问题清单、严重级别、处理结果、Reviewer、commit/产物 hash。

### 7. G5：测试验收

- **触发**：testing 节点；所有代码变更。
- **自动检查**：测试计划；必需测试类型；测试结果；验收标准映射；回归风险；覆盖率目标。
- **人工审批**：L2/L3 的验收签字；所有生产发布前的验收；L1 在测试通过且无验收歧义时可自动通过。
- **允许跳过**：仅文档变更时 G5 记为 N/A；无可行测试时必须显式记录风险并获用户接受，不得静默跳过。
- **不允许跳过**：核心/安全测试失败、验收标准未满足、生产发布前。
- **失败回退**：按缺陷类型返回 coding / analysis / design / requirements；生产发布不得继续。
- **版本绑定**：G5 必须记录被测试的 commit 或产物 hash；Coding 产生新代码版本后，旧版本的 G5 结果失效，必须重新测试。
- **通过状态**：`testing_approved`。
- **审计**：测试报告、环境、失败/重试、证据路径、commit/产物 hash。

### 8. G6：部署授权

- **位置**：**实际生产部署动作之前**。G6 通过后才允许执行部署；部署后的健康检查/冒烟/验收属于 Deployment Verification，不是 G6，也不能替代 G6。
- **不适用**：仅代码开发/交付、无生产部署计划的新项目、非生产环境部署；这些任务不要求 G6，安全限制按 R0–R4 权限模型处理。
- **触发**：实际生产部署动作（部署执行）；生产环境其他变更不自动触发 G6。
- **生产环境非部署变更**：生产配置、生产数据、认证/安全等非部署变更按 R3/R4 + SA 处理，不自动触发 G6；只有同时涉及实际生产部署时才增加 G6。
- **自动检查**：部署目标与环境；变更摘要；回滚方案；备份；监控/健康检查；G1–G5 记录；安全检查项。
- **人工审批**：所有生产部署必须人工授权；非生产环境是否需要审批按权限模型决定，不使用 G6。
- **允许跳过**：无部署任务时 G6 记为 N/A；非生产开发环境审批按权限模型处理，不标记为 G6。
- **不允许跳过**：实际生产部署动作；生产部署涉及的数据迁移、认证/安全变更或破坏性变更。
- **失败回退**：中止部署；如已部分执行，执行回滚并记录事件；不得把失败标记为成功。
- **通过状态**：`deployment_authorized` → 执行部署 → **Deployment Verification** → 验证通过后 `completed`。
- **审计**：部署记录、审批人、提交/产物 hash、回滚结果；部署后验证单独记录。
- **职责独立**：G6 不替代 G4/G5，不替代 R3/R4 操作权限检查，也不替代 SA 显式人工授权。

### 9. 任务类型与门禁

| 场景 | 必需门禁 | 按需门禁 | 说明 |
|------|----------|----------|------|
| 简单修改（L1） | G4（简化，独立 Review 不跳过）、G5（简化） | G1/G2/G3 可简化；G6 仅生产部署 | 不得跳过安全约束；纯文档变更 G4 可 N/A |
| Bug 修复（L2） | G4、G5 | G1/G2/G3 视范围；G6 仅生产部署 | Analysis → Coding → {Review(G4), Testing(G5)} → G4 AND G5 |
| 功能开发（L2/L3） | G1、G2、G3、G4、G5 | G6 仅生产部署 | 完整流程 |
| 系统重构（L3） | G1、G2、G3、G4、G5 | G6 仅生产部署 | 完整设计、Review、测试 |
| 新项目（L3） | G1、G2、G3、G4、G5 | G6 仅计划生产部署 | 代码交付不要求 G6 |
| 部署任务（L2） | 涉及代码/配置时 G4、G5；生产部署时 G6 | G1/G3 | 非生产部署按 R0–R4，不触发 G6；生产部署 G6 + R3 + SA；部署后验证独立 |
| 技术咨询 | 无代码门禁 | G1/G2 | 输出分析/设计产物 |

#### Bug Fix 执行语义

```text
Analysis
   ↓
Coding
   ↓
 ┌─────────────┐
 │             │
Review (G4)  Testing (G5)
 │             │
 └──────┬──────┘
        ↓
   G4 AND G5
        ↓
    Completed
```

- Review 与 Testing 是独立质量活动，允许并行，但 G4、G5 必须全部通过。
- Review 失败/严重问题返回 Coding；修复后必须重新执行 Review。
- Testing 失败返回 Coding；修复后必须重新执行相关测试。
- Testing、Lint、Typecheck 不能替代独立 Code Review。
- 简单修改 Workflow 的既有规则不变。

#### G6 适用性

| 任务类型 | G6 要求 |
|----------|---------|
| 仅代码开发和交付，不涉及生产部署 | **N/A** |
| 新项目开发，但不涉及生产部署 | **N/A** |
| 新项目开发，且计划生产部署 | 生产部署动作前必须通过 G6 |
| 非生产环境部署 | **N/A**，按 R0–R4 权限模型执行 |
| 生产部署 | 必须通过 G6 + R3 + SA |
| 生产数据库破坏性操作 | R4 + SA，并执行适用的独立安全控制；涉及生产部署时再加 G6 |

- G6 不能被 G4/G5 替代。
- G6 不能替代 R3/R4 操作权限检查。
- G6 不能替代 SA 显式人工授权。
- 不涉及生产部署的任务，不得被强制要求通过 G6。
- 非生产环境部署的安全限制由 R0–R4 权限模型负责。
- 生产部署授权必须在实际生产部署动作之前完成。
- 部署后的验证属于 Deployment Verification，不属于 G6。
- 所有任务类型示例必须与上述规则一致。

#### 部署任务复杂度示例

| 复杂度 | 示例 | G6 要求 | 权限/审批 |
|--------|------|---------|-----------|
| L1 | 非生产环境部署、本地容器启动 | **N/A** | R0–R3，按 R0–R4 权限模型；不触发 G6 |
| L2 | 生产环境部署 | 生产部署动作前必须通过 G6 | R3 + G6 + SA |
| L3 | 生产部署 + 数据迁移/架构变更/破坏性操作 | 生产部署动作前必须通过 G6 | R3/R4 + G6 + SA + 安全审查 |

### 10. 门禁关系与失败路径

```text
                 ┌── G4 Code Review ──┐
Coding ──────────┤                    ├── quality gate (G4 AND G5) ── G6 Deployment (仅生产部署)
                 └── G5 Testing ──────┘
```

- G4 与 G5 可并行，但**不能互相替代**；quality gate 必须两者都通过。
- Review 严重问题 → coding；Testing 失败 → 按缺陷类型回退。
- G6 不得绕过 quality gate；生产部署必须人工授权。
- 非生产部署不触发 G6；其安全限制按 R0–R4 处理。
- 简单任务可简化 G1–G3，但 G4（独立 Review）与 G5（测试）不得跳过；纯文档变更 G4 可 N/A。

#### G4/G5 版本绑定

1. G4 Code Review 与 G5 Testing 必须针对**同一代码提交或产物 hash**。
2. 每次 Review 和 Testing 必须记录对应的 commit / 产物 hash。
3. Coding 产生新的代码版本后，旧版本的 G4/G5 结果**不能**用于新版本的质量门禁。
4. 新版本必须重新执行 G4 和 G5。
5. 只有**同一版本**的 G4 和 G5 均通过，才能满足 quality gate。
6. 文档变更等无代码产物的情况按既有 N/A 规则处理。

### 11. 状态变化与审计

| 门禁通过 | 记录状态 |
|----------|----------|
| G1 | `requirements_approved` |
| G2 | `design_approved` |
| G3 | `plan_approved` |
| G4 | `code_review_approved` |
| G5 | `testing_approved` |
| G6 | `deployment_authorized` / 验证后 `completed` |

审计记录至少包含：门禁、task-id、节点、G4/G5 的 commit/产物 hash、输入产物引用（路径+版本+hash）、自动检查结果、人工决定、审批人、时间、有效期、失败回退路径。审计追加写入，敏感字段脱敏。

### 12. Builder Check（G2 的独立审查）

```yaml
builder_check:
  role: independent_reviewer
  checklist:
    - 是否遗漏用户需求？
    - 是否存在设计矛盾？
    - 是否有过度设计？
    - 是否存在安全风险？
    - 是否有无法落地的技术方案？
    - 是否存在未考虑的异常场景？
  outcomes:
    approved: 继续到编码阶段
    needs_revision: 返回设计阶段修改
    escalated: 升级给用户决策
```

### 13. 不可跳过规则

以下情况严禁跳过人工审批：

1. **实际生产部署动作** — G6 必须用户确认；生产环境的非部署变更按 R3/R4 + SA 处理，不自动触发 G6。
2. **数据破坏性操作** — 删除、修改生产数据。
3. **安全敏感变更** — 认证、授权、加密相关。
4. **用户明确要求的审批点**。

## 理由

1. **风险可控** — 关键决策有人工把关
2. **效率优化** — 简单任务快速通过
3. **责任明确** — 审批记录可追溯
4. **符合最佳实践** — 与业界 CI/CD 门禁理念一致
