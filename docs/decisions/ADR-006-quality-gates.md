# ADR-006：质量门禁与人工审批

**状态：** 已采纳  
**日期：** 2026-11-20

## 背景

软件研发的关键节点需要人工确认，防止 AI 擅自做出不可逆决策。

## 问题

如何设计质量门禁：
- 既保证质量又不阻碍效率
- 明确哪些必须人工审批
- 支持自动化检查 + 人工确认的组合

## 候选方案

### 方案 A：全自动执行

不设门禁，AI 自主完成所有步骤。

**优点：** 速度最快  
**缺点：** 风险高，不可逆错误难恢复

### 方案 B：全人工审批

每个步骤都等待人工确认。

**优点：** 控制力强  
**缺点：** 效率极低，不符合快速迭代需求

### 方案 C：分级门禁（选定）

根据任务类型和复杂度，设置不同级别的人工介入。

**优点：**
- 简单任务快速执行
- 复杂任务关键节点把关
- 平衡效率与质量

**缺点：**
- 需要定义分级规则
- 边界情况可能判断失误

## 决策

采用**方案 C：分级门禁**。

### 门禁分级

| 门禁 | 名称 | 触发条件 | 审批人 | 可跳过条件 |
|------|------|----------|--------|-----------|
| G1 | 需求确认 | L2/L3 任务 | 用户 | L1 任务 |
| G2 | 设计确认 | L3 任务 + Builder Check | 用户 | — |
| G3 | 开发计划 | L3 任务 | 用户 | L1/L2 任务 |
| G4 | 代码质量 | 所有任务 | 系统+用户 | 仅轻微问题 |
| G5 | 测试验收 | 所有任务 | 系统+用户 | 仅非核心测试 |
| G6 | 部署授权 | 生产环境变更 | 用户 | — |

### 自动 vs 人工判断

**自动判断：**
- 测试通过率
- 代码覆盖率
- 静态分析结果
- 安全检查项

**人工判断：**
- 需求理解是否正确
- 架构方案是否合理
- 设计是否有遗漏
- 严重问题是否可接受

## Builder Check 机制

在 G2（设计确认）引入独立审查：

```yaml
builder_check:
  role: independent_reviewer
  checklist:
    - 是否遗漏用户需求？
    - 是否存在设计矛盾？
    - 是否有过度设计？
    - 是否存在安全风险？
    - 是否有无法落地的技术方案？
    
  outcomes:
    approved: 继续到编码阶段
    needs_revision: 返回设计阶段修改
    escalated: 升级给开发者决策
```

## 不可跳过规则

以下情况严禁跳过人工审批：
1. **生产环境变更** — G6 必须用户确认
2. **数据破坏性操作** — 删除、修改生产数据
3. **安全敏感变更** — 认证、授权、加密相关
4. **用户明确要求的审批点**

## 理由

1. **风险可控** — 关键决策有人工把关
2. **效率优化** — 简单任务快速通过
3. **责任明确** — 审批记录可追溯
4. **符合最佳实践** — 与业界 CI/CD 门禁理念一致

## 后续影响

- P2 阶段实现 GateController
- 需定义每个门禁的详细检查清单
- 需实现审批记录存储
