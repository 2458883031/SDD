# 安全架构设计

## 1. 概述

SDD 安全架构区分两套不同的控制机制：

| 控制机制 | 回答的问题 | 本文档对应章节 |
|----------|------------|----------------|
| **权限控制（Permission）** | Agent 可以做什么？ | 第 2–4 节 |
| **审批控制（Approval）** | 某项高风险操作是否获得用户授权？ | 第 5 节 |

权限控制决定能力边界；审批控制决定单次高风险操作是否放行。两者不能互相替代：有权限不等于已获审批，已获审批也不应获得超出权限的能力。

> **P0 状态：In Review。** 本文档是安全架构要求，不代表相关机制已经实现。实现状态见第 9 节。

## 2. 权限模型（R0–R4）

### 2.1 权限级别

> 命名说明：权限级别使用 **R0–R4**，与项目阶段 P0–P7、测试层级 T1–T4 区分。

| 级别 | 名称 | 允许的能力 | 典型工具 | 默认环境 |
|------|------|------------|----------|----------|
| **R0** | 只读 | 读取允许访问的项目文件、查看状态 | read、ls、git status、sessions read | 任意（受路径边界限制） |
| **R1** | 普通写入 | 修改项目文件、生成文档 | write、edit、apply patch | 开发/测试 |
| **R2** | 受控执行 | 运行测试、构建、格式化、受限脚本、只读查询 | exec（允许列表）、测试运行器、git 读写 | 开发/测试 |
| **R3** | 高风险操作 | 部署、数据库迁移、外部网络写操作、非生产环境管理 | deploy、migration、network allowlist、package manager | 开发/测试/预发布；生产需额外授权 |
| **R4** | 严重敏感操作 | 生产数据破坏性操作、敏感凭证读取、不可逆高危操作 | prod admin、secret read、高危 exec | 仅显式授权 |

> 说明：R3 的“高风险操作”是任务书规定的风险类别名称；具体能力见示例列，不代表与其他级别的能力描述存在冲突。

**统一约束：**

1. **生产部署 = R3 + G6 + SA**（SA：显式人工授权）。
2. **生产数据库破坏性操作 = R4 + SA**；涉及实际生产部署时还需 G6。
3. **敏感凭证读取 = R4 + SA**；不得由 Agent 自行批准。
4. **高风险 Shell 操作**按实际影响范围定为 R2/R3/R4：普通测试脚本 R2；部署/迁移 R3；不可逆或生产破坏 R4。
5. **权限与审批分离**：R 级别决定能力上限，G1–G6 与 SA 决定单次放行。
6. **G6 是质量与发布门禁，不是权限检查**；G6 通过不代表已获得 R3/R4 权限，反之亦然。
7. **SA 是显式人工授权**，不得被自动化检查、门禁通过或 Agent 自行批准替代。
8. **默认拒绝**未声明的权限。
9. **不得通过降低任务复杂度绕过权限要求。**

### 2.2 默认权限与最小权限

- **默认拒绝**：未明确授予的能力不可用。
- **最小权限**：Skill 只获得完成当前节点所需的最小级别；任务结束或节点完成后回收。
- **按阶段授予**：默认权限配置只是上限建议，实际授予由 Task Context 和安全策略共同决定。
- **禁止绕过**：不得通过降低任务复杂度、拆分任务或新建会话绕过权限要求。

```yaml
# 默认权限上限（不是自动授权）
default_permission_ceiling:
  requirements-clarity: [R0]
  analysis: [R0, R1]
  design: [R0, R1]
  coding: [R1]
  code-review: [R0, R1]
  testing: [R1, R2]
  deployment: [R2, R3]      # 生产部署还需 G6 + 显式安全授权
  documentation: [R0, R1]
  feedback-loop: [R0]
```

- `requirements/analysis/design/review/documentation/feedback` 默认不得写生产环境。
- `coding/testing` 默认不得访问生产凭证或生产数据。
- `deployment` 只有进入部署节点后才获得环境凭证；不得把生产凭证预先放进 Task Context。

### 2.3 权限申请与有效期

1. Agent 提交权限申请：范围、原因、目标环境、预计时长。
2. 用户或策略控制器批准后，授予**临时权限（lease）**，记录到审计日志。
3. 临时权限必须有过期时间（默认不超过当前节点/任务）。
4. 到期自动回收；任务结束、节点失败或审批撤销时立即回收。
5. 被拒绝时停止操作，不得静默降级为更宽松的路径。

### 2.4 权限转授

- **默认禁止**：Agent 不得把自己的权限转交给其他 Agent。
- 如策略允许，只能转授**子集**，必须显式、限时、记录 `delegated_from` / `delegated_to`，且不得转授 R4。
- 子 Agent 的权限不得超过父 Agent；不得通过新会话/新 Agent 绕过限制。

### 2.5 审计记录（权限维度）

每次权限授予、使用、拒绝、回收记录：

- 谁（Agent / 用户）
- 何时（时间戳）
- 哪个任务（task-id）与节点
- 授予/使用的权限级别与范围
- 结果（成功/拒绝/失败）
- 对应审批记录（如有）

## 3. 文件系统访问边界

### 3.1 允许与拒绝路径

```yaml
# 架构要求，不是当前已实现的配置
file_boundaries:
  allowed:
    - "${project_root}/**"
    - "${project_root}/artifacts/**"
    - "${explicit_temp_dir}/**"
  denied:
    - "${HOME}/.ssh/**"
    - "${HOME}/.aws/**"
    - "${HOME}/.config/**"        # 平台配置与凭证
    - "/etc/**"
    - "C:\\Windows\\**"
    - "其他项目根目录/**"
  git:
    read: allowed
    write: 仅通过受控 git 工具，不直接改 .git/
```

### 3.2 路径校验规则

1. **规范化后校验**：解析绝对路径、符号链接和 `..`，再判断是否在允许根目录内。
2. **禁止路径穿越**：拒绝解析后越出允许根目录的路径。
3. **符号链接**：不跟随指向允许范围外的链接。
4. **大小写与盘符**：Windows 下按大小写不敏感处理；跨平台实现必须显式处理。
5. **写入隔离**：每个任务只能写自己的 `artifacts/{task-id}/` 和工作区允许路径；其他任务产物只读。

## 4. Shell、网络与环境边界

### 4.1 Shell 权限

- **允许列表优先**：按 Skill/阶段配置可执行命令类别（测试、构建、格式化、只读查询）。
- **默认拒绝**：未在允许列表中的命令不得执行。
- **黑名单只是补充**：字符串黑名单（如 `rm -rf /`）不能作为完整安全边界；真正的边界是权限级别、沙箱、路径限制和审批。
- **禁止不可信拼接**：不得把用户输入直接拼进 shell 命令；使用参数化调用。
- **超时与并发**：节点有超时；并发进程有上限（建议 5 个，单 Skill 2 个）。
- **高风险命令**：删除、磁盘写入、权限修改、下载后执行等按实际影响范围定为 R2/R3/R4；不可逆或生产破坏为 R4，需 SA。

### 4.2 网络权限

- **默认拒绝外部网络**；只允许显式 allowlist 的目标。
- 外部 API 访问需要显式授权，并遵循网络 allowlist；实际生产部署相关请求必须遵循 G6 授权规则；生产环境非部署 API 请求不自动触发 G6，按 R3/R4 + SA 处理。
- 敏感凭证不得出现在 URL、日志、命令历史或模型上下文中。
- 出站请求应记录目标、用途、结果；不得绕过 allowlist 使用代理/隧道。

### 4.3 环境权限

| 环境 | 默认允许的操作 | 禁止 |
|------|----------------|------|
| 开发（dev） | R0–R2，必要时 R3（非生产依赖/容器） | 生产凭证、生产数据 |
| 测试（test） | R0–R3，自动化测试、非生产部署 | 生产凭证、生产数据库写入 |
| 生产（prod） | 仅 deployment 节点执行生产部署：R3 + G6 + SA；生产环境非部署操作按 R3/R4 + SA，不自动触发 G6 | coding/testing/analysis 直接访问生产 |

- 上表的 R3 + G6 + SA 仅针对生产部署执行；不是所有生产环境操作都必须经过 G6。

- 生产凭证只在部署节点临时注入，不写入 Task Context，不落入日志。
- 不同环境的配置和凭证必须隔离；不得用同一凭证跨环境操作。

## 5. 审批控制

### 5.1 审批与权限的区别

- **权限**：能力上限，长期/按阶段授予。
- **审批**：单次操作放行，绑定具体操作、目标、环境和风险。
- **G6 不是权限检查**：G6 是质量与发布门禁；通过 G6 不等于获得 R3/R4 权限，获得 R3/R4 也不等于已获 G6，也不等于已获 SA。
- 有 R3 权限不代表可以部署生产；生产部署仍需 G6 + SA。
- 通过审批不自动提升权限级别；需要更高权限时仍要单独申请。

### 5.2 审批类型

| 类型 | 来源 | 用途 |
|------|------|------|
| G1–G6 | [ADR-006](../decisions/ADR-006-quality-gates.md) | 阶段质量门禁与部署授权 |
| 显式安全授权（SA） | 本文档 | 高风险操作的单次用户授权，记录在审计日志；不是新的流程引擎或门禁组件 |

SA 必须绑定：操作、目标、环境、风险等级、有效期、批准人、回滚方案。SA 不能被批量授予，也不能被其他审批替代。

### 5.3 风险等级与审批映射

| 风险 | 示例操作 | 最低权限 | 必需审批 | 环境 | 审计/回滚 |
|------|----------|----------|----------|------|-----------|
| 低 | 写项目文件、运行只读查询 | R1 | 无需 | dev/test | 版本控制记录 |
| 中 | 安装依赖、运行测试/构建、访问 allowlist 外部 API | R2–R3 | 外部 API 需显式授权 | dev/test | 审计日志 |
| 高 | 修改认证/授权代码 | R2 | G2/G4 + 显式安全审查 + 适用 SA；不因生产相关自动触发 G6 | dev/test/prod | 审计 + 回滚方案 |
| 高 | 修改生产配置 | R3 | SA + 配置备份；仅同时涉及实际生产部署时加 G6 | prod | 审计 + 回滚方案 |
| 高 | 生产部署 | R3 | G6 + SA + 回滚方案 | prod | 审计 + 回滚方案 |
| 严重 | 删除生产数据、修改生产数据库、读取敏感凭证、高风险 Shell | R4 | SA + 安全审查 + 备份/恢复；仅涉及实际生产部署时加 G6 | prod/受限 | 备份 + 恢复演练 + 审计 |

**高风险操作清单（必须显式处理，不能只依赖 G6）：**

1. 删除重要数据 — R4 + SA + 备份/恢复方案 + 审计。
2. 修改认证与权限逻辑 — R2 + G2 设计审查 + G4 代码审查 + 显式安全审查 + 适用 SA；不因生产相关自动触发 G6。
3. 修改生产配置 — R3 + SA + 配置备份；如果同时涉及实际生产部署，再增加 G6。
4. 修改生产数据库 — R4 + SA + 备份/回滚 + 安全审查；只有同时涉及实际生产部署时才增加 G6。
5. 生产部署 — R3 + G6 + SA + 回滚方案。
6. 访问敏感凭证 — R4 + SA + 密钥管理服务；不得写入日志或上下文。
7. 执行高风险 Shell — R2/R3/R4 按影响范围 + 相应 SA/审计；禁止在宿主直接执行不可逆命令。

> G6 只由实际生产部署触发；R3/R4 是操作权限等级；SA 是单次高风险操作的显式人工授权。三者互不替代。

### 5.4 审批流程

```text
1. Agent 检测到需要审批的操作
2. 暂停执行，生成审批请求（操作、目标、环境、风险、影响、回滚方案）
3. 用户/策略控制器审阅
4. 显式批准或拒绝
5. 记录审批（who/when/what/scope/expiry）
6. 在权限与审批范围内执行
7. 记录结果；失败时按回滚方案处理
```

**规则：**

- 超时、沉默、默认值都**不等于批准**。
- 审批只对指定操作/目标/有效期有效，不得复用。
- 审批被拒绝时停止，不得换路径绕过。
- 严重风险操作不得由 Agent 自批或自动通过。

### 5.5 不可跳过

- 生产环境变更（按 R3/R4 + SA；实际生产部署另加 G6）
- 数据破坏性操作
- 安全敏感变更（认证、授权、加密）
- 敏感凭证访问
- 用户明确要求的审批点

低风险任务可以使用简化流程，但不能绕过上述安全约束。

## 6. Skill 执行安全

### 6.1 输入验证

每个 Skill 在执行前验证：

1. 输入格式是否符合契约。
2. 路径是否在允许范围内（规范化后校验）。
3. 是否包含路径穿越、命令注入或不可信内容。
4. 所需权限是否已授予；未授予则请求或停止。

### 6.2 输出过滤

1. 扫描敏感信息（API Key、Token、密码、私钥）。
2. 验证生成代码不含已知危险模式。
3. 检查写入路径是否在允许目录。
4. 输出中的敏感值替换为 `[REDACTED]`；日志不保留原文。

### 6.3 危险操作处理

危险操作必须经过权限 + 审批 + 审计，不得只靠字符串黑名单。黑名单可作为额外防线，但不能作为唯一安全边界。

## 7. 凭证和敏感信息管理

### 7.1 检测模式（辅助，不是边界）

- API Keys：`sk-[a-zA-Z0-9]{20,}`
- Tokens：`ghp_[a-zA-Z0-9]{36}`
- Passwords：环境变量名/值中包含 `password`、`secret`
- Private Keys：`-----BEGIN ... PRIVATE KEY-----`

检测用于告警和脱敏，不能替代权限、沙箱和审批。

### 7.2 存储与注入

```yaml
# 架构要求
credential_handling:
  storage:
    - "平台密钥管理 / 环境变量注入"
    - "不得硬编码、提交版本控制或写入日志"
  injection:
    - "仅在需要的节点临时注入"
    - "最小作用域、最短有效期"
  redaction:
    - "输出、日志、审计记录中统一脱敏"
```

### 7.3 多 Agent 场景

- Agent 之间不传递原始凭证；通过任务上下文传递**凭证引用**，由有权限的适配器解析。
- 不得把凭证写入 artifacts、context.json 或会话消息。

## 8. 审计、回滚与多 Agent 信任边界

### 8.1 审计日志

```json
{
  "event_id": "uuid",
  "timestamp": "ISO8601",
  "actor": {"type": "agent", "id": "agent-id"},
  "task_id": "task-...",
  "node_id": "deployment",
  "action": "deploy_to_production",
  "target": "prod-cluster",
  "permission": "R3",
  "approval": {
    "type": "G6+SA",
    "approved_by": "user-id",
    "approved_at": "ISO8601",
    "expires_at": "ISO8601"
  },
  "result": "success|failed|cancelled",
  "rollback_available": true,
  "redacted": true
}
```

要求：追加写入、不可静默修改、敏感字段脱敏、保留期限可配置（建议 90 天）。

### 8.2 回滚

- 变更前备份/快照；删除优先软删除或回收站。
- 每个高风险操作必须有回滚方案和验证步骤。
- 自动回滚：测试失败、健康检查失败、用户请求。
- 人工回滚：生产事故、性能退化、安全事件。
- 回滚结果记录审计；回滚失败升级人工处理。

### 8.3 多 Agent 信任边界

- 独立 workspace、独立会话存储、独立凭证作用域。
- 同任务共享：通过 `artifacts/{task-id}/` 只读引用，不共享写入目录。
- 跨任务读取：必须显式引用（路径 + 版本 + hash），不得遍历其他任务目录。
- 权限转授：默认禁止；允许时只能转授子集、限时、审计，且不得转授 R4。
- 系统 Agent 可协调，但不能越权或绕过用户审批。

| Shell 允许列表/沙箱 | 必须优先允许列表 | **未实现**（P2） |
| 网络 egress 控制 | 默认拒绝 + allowlist | **未实现**（P5） |
| G1–G6 审批执行 | 规则见 ADR-006 | 仅设计，**未实现**（P2） |
| 安全审计日志 | 追加写入、脱敏 | **未实现**（P2/P5） |
| 凭证管理/脱敏 | 引用传递、临时注入 | **未实现**（P5） |
| 回滚与恢复 | 高风险操作必备 | **未实现**（P5） |
| OpenClaw 平台审批 | 平台自身审批机制（范围未验证） | 存在与否及覆盖范围未验证；即使存在，也**不是 SDD 安全模型的实现** |

**说明：** 当前 OpenClaw 运行环境可能具备自身的命令审批机制；其存在范围和对 SDD 的覆盖程度均未验证。它不能替代 SDD 的 R0–R4、默认拒绝、Task Context 权限和审计要求。P0 不宣称 SDD 安全机制已经可用。

## 10. 安全测试要求

安全测试属于 P5–P7 规划，测试架构见 [testing-architecture.md](./testing-architecture.md)。至少覆盖：

- 输入注入、路径穿越、命令注入
- 权限提升、权限转授越权
- 敏感信息泄漏与日志脱敏
- 审批绕过、超时误判
- 回滚失败与恢复

## 11. 风险与限制

1. **安全机制未实现** — P0 只有设计，不能把文档当作已具备的防护。
2. **平台差异** — 各平台的沙箱、审批和凭证机制不同，适配层需逐平台验证。
3. **黑名单局限** — 字符串过滤不能作为完整边界；必须依赖权限、沙箱和审批组合。
4. **性能开销** — 审计、脱敏和审批会带来额外开销，需要在实现阶段评估。
