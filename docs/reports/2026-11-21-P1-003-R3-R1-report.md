### 2.1 关键规则

- **双上游绑定：** `requirements_ref` 与 `analysis_ref` 均为必需，必须显式记录 path/version/sha256/type；不得隐式使用“最新版本”。
- **推荐不是决定：** Analysis 推荐仅供参考；Design 可选择其他方案，但必须记录 `deviation_from_recommendation`、理由、证据和重新评估条件。
- **不输出 plan：** Design 只输出 `type=design`；Planning 归 Orchestration，产生 Plan Artifact；G3 审查/批准，不生成。
- **G2 分离：** ADR-006 仍是 G2 权威；ADR-009 仍是 Proposed；Design 不写 GateDecision/Approval，不输出 `design_approved`/`gate_approved`/`confirmation_ref`。
- **追踪闭环：** Requirements 与 Analysis 的关键条目必须有 disposition 或理由，不得静默遗漏。
- **L1 防过度设计：** L1 只需轻量设计摘要、受影响范围、至少一个 lightweight 决策、AC/验证方法和风险/unknown；不强制完整架构章节。
- **三层状态分离：** Skill status ≠ Artifact status ≠ Gate status；`ok` 不等于 G2 PASSED。

## 三、跨模块边界核验

### 3.1 Requirements → Design

- Design 输入显式引用 Requirements Artifact，类型必须为 `requirements`；
- 不重写/重新定义 Requirements；
- Requirements traceability 覆盖 FR/NFR/constraints/dependencies/assumptions/unknowns/open questions/AC/non-goals/source refs；
- blocking 未决项不得输出完整 `ok`；
- 需求变化需重新评估并生成新 Design 版本；自动失效 Runtime 未实现。

### 3.2 Analysis → Design

- Design 输入显式引用 Analysis Artifact，类型必须为 `analysis`；
- Analysis 推荐不是强制决定；
- 候选/风险/unknown/open question/design consideration 必须有 adopted/adapted/rejected/retained/N/A/deferred 处理；
- 偏离推荐必须记录理由和证据；
- Analysis blocking 未闭合时不得 `ok`；
- 不把 Analysis 内容重新包装成 Design 结论。

### 3.3 Design → Planning

- Design 输出设计规格，不输出 implementation-plan；
- Planning 是 Orchestration 内部活动；
- Planning 根据 Requirements/Analysis/Design 生成 Plan Artifact；
- G3 审查/批准 Plan，不生成 Plan；
- 当前 P1-002 `feature-development.yaml` 在 G2 后直接 G3、没有 plan 节点/生产者；该缺口保留给 R4，R1 未修改 P1-002。

### 3.4 Design → Coding

- 提供组件/模块 ID、职责、依赖方向；
- 提供接口契约、数据模型/数据流、状态/转换、失败处理、安全/性能约束、AC 验证方法；
- Coding 遇到设计缺失必须反馈/`needs_input`，不得擅自做重大架构决策；
- Coding Skill 尚未实现，R1 只定义标准边界。

### 3.5 Design → Code Review / Testing

- Code Review 用组件/接口/数据/决策/约束作为设计符合性基准；
- Testing 用 `test_strategy` 与 AC 映射设计测试；
- Design test strategy 不是测试结果，不产生 G5 证据；
- Design 不替代 G4/G5，不输出 `code_review_approved`/`testing_approved`；
- Design 变更需评估代码、测试、部署影响。

### 3.6 G2 / Builder Check

- G2 在 Design 完成后、Planning/Coding 前由 Orchestration 挂载；
- ADR-006 §4 是 G2 权威；ADR-009 Proposed 不是已生效规则；
- 当前 GateDecision Schema 的 PASSED 要求 `subject_hash`，但未强制 Design path/version/type；G2 的 Approval 未强制 subject_hash；无 G2 专项示例；
- 标准提供 G2 检查项到 Design 输出的映射和 Builder Check 独立性要求；
- 未实现 G2 审批、GateController、自动失效或 Approval 构造；
- 未把 ADR-009 写成 Accepted。

## 五、发现的问题与修复

OpenClaw 通过既有 SDD 会话完成初稿；Claude Code 独立复核时发现并修正了以下问题：

1. **标准状态编号**：初稿写 `P1-003-R3 Draft`，改为 `P1-003-R3-R1 Draft`，与阶段一致。
2. **安全架构链接错误**：§14 链接指向不存在的 `docs/standards/security-architecture.md`，改为 `../architecture/security-architecture.md`。
3. **L1 与架构字段矛盾**：初稿将 `architecture_overview` 列为 Required，同时 L1 允许跳过完整架构章节；补充 L1 可只写变更影响/受影响组件/接口/数据。
4. **Analysis Traceability 分类不一致**：初稿列为 Conditional Required，但 Analysis 输入为必需；改为 Required。
5. **Analysis traceability 缺少 disposition**：补充 adopted/adapted/rejected/retained/N/A/deferred 规则，防止静默忽略候选/风险/设计考虑。
6. **Planning 术语易混淆**：初稿写 Planning “生成 implementation-plan”；改为“生成 Plan Artifact（实施计划）”，避免把 Design 的禁止字段与 Planning 产物混淆。
7. **G2 边界不够可审查**：补充 G2 检查项到 Design 字段的映射、Builder Check 独立性和设计 Artifact hash 证据边界。
8. **needs_approval 与 G2 混淆风险**：明确 Design 不得把 G2 本身作为审批请求，G2 由 Orchestration 在 Design 完成后执行。
9. **Required 可空数组矛盾**：明确 Required 字段必须存在，标为“可空”的数组存在但允许为空。
10. **Design 变更影响不足**：补充受影响组件/接口/数据/状态/安全/测试/部署、是否重做 Coding/Review/Testing，以及 ADR-009 仍未生效。
