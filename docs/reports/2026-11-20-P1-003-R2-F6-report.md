## 二、F6-A：规范引用格式

### 2.1 接受的形式

`resolution_evidence_refs` 的每个元素必须完整匹配以下之一：

1. 裸 SHA-256：`^[a-f0-9]{64}$`；
2. 版本化引用：`^(?!(?:.*[a-f0-9]{64}){2}).+@[0-9]+#[a-f0-9]{64}$`。

即 `path@version#sha256`，其中 SHA-256 为小写、恰好一个、位于引用末尾。

### 2.2 拒绝的形式

以下情况全部 **fail-closed**，不得被当作 `resolved` 证据：

- `path#sha256`（未定义 `@version`，不作为规范形式）；
- 缺少 SHA-256；
- SHA-256 后存在额外字符；
- SHA-256 不在末尾；
- 引用中出现多个 64 位十六进制摘要；
- 摘要重复；
- 引用前部存在另一个 64 位十六进制路径片段；
- 大写或混合大小写摘要；
- 仅包含某个 64 位子串、但整体不符合规范格式的引用。

### 2.3 解析器修复

`artifact_sha()` 不再使用无锚点 `re.search(r"[a-f0-9]{64}")`。现在：

1. 先以 `^[a-f0-9]{64}$` 判定裸 SHA-256；
2. 再以 `^.+@[0-9]+#[a-f0-9]{64}$` 判定版本化引用；
3. 版本化引用必须通过 `findall(r"[a-f0-9]{64}")` 确保全文恰好一个摘要；
4. 其他任何形式返回 `None`。

因此伪造的 64 位前缀不会再被优先提取为 Requirements SHA-256。

### 2.4 Requirements Artifact 身份

- Requirements 身份仍由规范解析出的 SHA-256 判定；
- 同一 SHA-256 的任何不同 path、目录、文件名或别名仍是同一 Artifact；
- 该身份不能作为 `resolved` 证据，也不能作为独立证据；
- `source_requirements_ref`、普通 `source_refs`、纯 path、`user_stated`/`assumption` 陈述仍不构成解决证据。

### 2.5 Schema 收紧

`output.schema.json` 的 `resolution_evidence_refs.items` 由“包含 SHA 子串”改为完整格式约束：

- `oneOf` 仅接受裸 SHA-256 或版本化引用；
- 版本化 pattern 增加单摘要负向前瞻，拒绝路径中另有 64 位十六进制片段；
- 大写/混合大小写、额外后缀、缺失摘要均不能通过；
- `path#sha256` 因缺少 `@version` 不能通过。

## 三、F6 测试

### 3.1 新增负向测试（11 个）

1. 伪造 64 位 SHA 前缀 + Requirements SHA 后缀：拒绝；
2. 一个引用中含两个不同 SHA：拒绝；
3. Requirements SHA 位于中间而非末尾：拒绝；
4. Requirements SHA 前另有 64 位十六进制路径片段：拒绝；
5. Requirements SHA 后有额外字符：拒绝；
6. 缺少摘要：拒绝；
7. 摘要重复：拒绝；
8. 大写/混合大小写摘要：拒绝；
9. 多 SHA 别名放入 `facts.evidence_refs`：拒绝；
10. 多 SHA 别名放入 `candidate_solutions.evidence_refs`：拒绝；
11. 多 SHA 别名放入 `risk_assessment.evidence_refs`：拒绝。
