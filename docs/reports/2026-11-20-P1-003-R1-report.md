## 二、Requirements 标准要点

### 2.1 职责边界

**负责：**

- 用户请求解析、目标/范围/非目标；
- FR/NFR 拆分；
- 约束、依赖、假设、未知项；
- 模糊点、冲突点、澄清问题；
- 可验证验收标准；
- 需求来源、版本、变更影响；
- 为 Analysis 提供稳定输入。

**不负责：**

- 技术方案/架构/技术选型（Analysis/Design）；
- 影响/可行性完整分析（Analysis）；
- 设计规格/接口/数据/测试策略（Design）；
- Planning/G3（Orchestration）；
- G1/G2/G3/SA 批准；
- 伪造用户确认。

### 2.2 输入契约

- `request`（必需）；
- `project_context`（可选）；
- `constraints`（可选）；
- `existing_requirements`（可选）：字符串兼容旧输入，推荐 `{path,version,sha256,type}`；
- `change_request`（可选）：`reason`、`requested_changes`、`previous_requirements`。

### 2.3 输出契约

复用 P1-001 统一信封；`data.requirements` 支持：

- `goal/scope/non_goals/constraints`；
- `functional_requirements`、`non_functional_requirements`；
- `dependencies`、`assumptions`、`unknowns`、`open_questions`、`ambiguities`、`conflicts`；
- `acceptance_criteria`（字符串或带 `verification` 的对象）；
- `source_refs`、`change_impact`、`requirements_version`。

### 2.4 事实/假设/未知项

| 类型 | 规则 |
|------|------|
| `user_stated` | 用户明确表达，可进入 FR/NFR |
| `evidence_backed` | 仓库代码/文档可验证，必须有 `evidence_refs` |
| `assumption` | 只能进入 `assumptions`，状态只能 `unconfirmed` |
| `unknown` | 进入 `unknowns`，标注 `blocking` |

- 未确认假设不得升级为用户事实；
- 用户未回答的问题不得伪造为已解决；
- `status=ok` 不得含 blocking unknown/question、未解决冲突/模糊点；
- `status=ok` 不代表 G1 通过或用户确认。

### 2.5 需求变更

`change_impact` 包含：

- `previous_ref`（旧 Artifact version+sha256）；
- `change_reason`；
- `changed_items`、`affected_requirement_ids`；
- `downstream_impact`（analysis/design/plan）；
- `gate_invalidation`（G1/G2/G3）。

只定义静态契约；自动失效 Runtime 未实现。

## 三、G1 与用户确认边界

- Requirements Skill 的 `status=ok` 只表示需求基线处理完成。
- 用户确认由 G1 GateDecision / Approval 记录。
- Skill 输出不允许 `confirmation_ref`、`gate_approved`、`confirmed_by`。
- 测试新增 `confirmation_ref` 负向 Schema 用例；任何伪造确认都会失败。
- ADR-009 Proposed 建议 G1 绑定 requirements artifact version+sha256；在 ChatGPT 接受前不生效。
