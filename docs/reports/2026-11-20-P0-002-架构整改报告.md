## 一、任务执行摘要

P0-002 针对 ChatGPT 评审提出的 8 类架构一致性问题，在不推翻现有 P0 设计的前提下完成收敛：

- 六个核心概念与职责边界统一，`system-architecture.md §2` 成为唯一定义来源。
- G1–G6 统一由 `ADR-006` 定义，其他文档只引用，不再重复定义规则。
- Skill 通用规范与平台元数据分离，核心 `SKILL.md` 移除平台专属字段。
- Workflow DAG 明确：Code Review 与 Testing 并行、共同构成质量门禁、Deployment 不得绕过。
- 权限（R0–R4）与审批（G1–G6 + 显式安全授权）分离，补充风险矩阵与实现状态。
- 六个平台清单统一（含 OpenClaw），未实测能力统一标注为设计假设/未验证。
- Task Context / Artifact 的创建、状态、归属、写入、并发、版本和归档规则明确。
- 文档链接、目录树、CLI 示例、状态标注完成一致性修正。

**结论：** 8 项任务在设计层面全部关闭；所有涉及运行时的能力仍标记为未实现。建议提交 ChatGPT 复审，不启动 P1。

## 三、逐项整改情况

### P0-002-01 核心概念与职责边界

**修改前：** Orchestration 同时被描述为编排层、编排引擎和 `skills/development/orchestration/` Skill；Workflow 与 Skill 集合混用；L6 被画成核心向下的一层。

**修改后：**

- 在 [system-architecture.md §2](../architecture/system-architecture.md#2-核心概念权威定义) 建立六个概念的唯一定义：
  - Agent：有角色、任务边界、上下文和权限的执行主体。
  - Orchestration：任务识别、拆解、路由、协调、状态和结果汇总的运行时能力。
  - Workflow：步骤、依赖、分支、并行和门禁的流程定义，不是 Skill 集合。
  - Skill：封装专业能力的可复用能力包，不直接拥有系统权限。
  - Tool：文件、Shell、Git、浏览器、测试等操作原语。
  - Platform Adapter：把核心契约映射到平台，不决定核心流程。
- 明确 `orchestration` Skill 只是入口，编排引擎位于 `core/orchestration/`（P2 规划），两者不等同。
- 重画组件关系图和依赖关系图：核心（L1–L5）只依赖端口；L6 是适配边界，依赖方向为 `L6 → Core Ports`；核心不 import 平台实现。
- 修正原“L4/L5 双向依赖”为 `L4 → L5`，消除循环依赖歧义。
- [module-architecture.md](../architecture/module-architecture.md) 区分 `orchestration-engine` 与 `orchestration-skill`，并更新模块依赖。

**验证：** 全文检索确认没有把 Orchestration 同时定义为 Skill 和引擎的表述；ADR-001、ADR-003 已同步修订。

### P0-002-02 G1–G6 质量门禁统一

**修改前：** orchestration、testing、security、ADR-006 对 G4/G5/G6 的触发、审批、跳过条件存在差异；G5 曾被写成“所有任务人工审批”，G4/G5 关系不清。

**修改后：**

- [ADR-006](../decisions/ADR-006-quality-gates.md) 成为 G1–G6 的**唯一权威定义**。
- 每个门禁定义：触发、自动检查、人工审批、允许跳过、不允许跳过、失败回退、通过状态、审计。
- 明确：
  - G4 与 G5 独立，可并行，但不能互相替代；质量门禁 = G4 AND G5。
  - G6 依赖质量门禁；生产部署必须人工授权。
  - 不是所有门禁都需要人工审批；低风险任务可简化，但不能绕过安全约束。
  - 超时、沉默不等于批准；严重风险不得自批。
- [orchestration-architecture.md](../architecture/orchestration-architecture.md) 只保留门禁挂载位置，不重复规则。
- [testing-architecture.md](../architecture/testing-architecture.md) 与 [security-architecture.md](../architecture/security-architecture.md) 统一引用 ADR-006。
- 增加简单修改、Bug 修复、功能开发、系统重构、新项目、部署任务、技术咨询的场景映射。

**验证：** G1–G6 只在 ADR-006 出现完整规则；其他文档均为引用或挂载位置说明。

### P0-002-03 通用 Skill 规范与平台元数据分离

**修改前：** 核心 `SKILL.md` 元数据示例包含 `metadata.openclaw.requires`、`primaryEnv` 等平台专属字段；测试示例使用了不存在的 `openclaw agent --skill` 参数。

**修改后：**

- [skill-architecture.md](../architecture/skill-architecture.md) 定义两层规范：
  - 核心：`name`、`description`、可选平台无关 `requires`（runtime / tools / permissions）。
  - 平台：`platforms/<platform>/skill-metadata.yaml`，负责发现路径、触发映射、bins/env、调用参数。
- 明确 `requires.permissions` 是需求声明，不是授权；实际授权由安全模型决定。
- [ADR-002](../decisions/ADR-002-skill-standard.md) 同步修订字段归属与处理规则。
- CLI 示例增加状态标注：已验证 / 伪代码 / 规划示例 / 无效；删除 `openclaw agent --message ... --skill` 这种无效命令，并明确标为禁止。
- 平台目录规划包含六个平台，每个平台有 `skill-metadata.yaml`。

**验证：** 核心文档中不再有可执行的平台专属元数据示例；`metadata.openclaw` 只出现在“禁止”说明中。

### P0-002-04 Workflow DAG 与质量门禁依赖

**修改前：** 模块依赖图是线性的（testing → deployment），没有明确 Code Review 与 Testing 的并行、双门禁和失败回退。

**修改后：**

- [orchestration-architecture.md](../architecture/orchestration-architecture.md) 定义 Workflow DAG 执行语义：
  - 节点字段：id、type、skill/tool、depends_on、mode、condition、parallel_group、inputs/outputs、on_success/on_failure、retry、timeout、approval、gate。
  - 状态：pending / running / awaiting_approval / paused / completed / failed / aborted。
- 功能开发 DAG：`coding → {code-review(G4), testing(G5)} → quality gate(G4 AND G5) → deployment(G6) → verification → documentation → feedback`。
- Review 与 Testing 可并行，但都不能替代对方；Deployment 不得绕过质量门禁。
- 失败路径：Review 严重问题 → coding；Testing 失败按缺陷类型回到 coding/analysis/requirements；G6 失败 → 中止/回滚。
- 重试、超时、审批暂停/恢复有明确语义；超时不等于批准。
- 提供功能开发、Bug 修复、简单修改三个 Workflow 示例（设计示例，不是可执行 Schema）。
- [module-architecture.md](../architecture/module-architecture.md) 更新模块依赖图和 Task Context 引用。
- [ADR-003](../decisions/ADR-003-orchestration.md) 同步修订调度策略与门禁引用。

**验证：** DAG 中 Deployment 的唯一入口是 quality gate；Review 与 Testing 同时是 quality gate 的前置。

### P0-002-05 安全权限与审批控制模型

**修改前：** R0–R4 只描述权限等级，未定义权限如何约束实际执行；高风险操作被简单归入 G6；字符串黑名单被当成安全边界。

**修改后：**

- [security-architecture.md](../architecture/security-architecture.md) 明确区分：
  - 权限控制：Agent 可以做什么（R0–R4、默认拒绝、最小权限、权限 lease、转授限制）。
  - 审批控制：单次高风险操作是否放行（G1–G6 + 显式安全授权 SA）。
- 补充文件、Shell、网络、环境边界；明确黑名单只是补充，不是完整边界。
- 补充权限申请、有效期、转授、审计。
- 定义风险矩阵：低/中/高/严重 → 最低权限、必需审批、环境、审计/回滚。
- 高风险操作（删除数据、认证/权限、生产配置、生产数据库、生产部署、敏感凭证、高风险 Shell）分别映射到 R 级别 + G 门禁 + 显式授权 + 审计/回滚，明确不能只依赖 G6。
- 增加“实现状态”表：所有运行时安全机制均标记为未实现（P2/P5），仅 OpenClaw 平台自身 exec 审批存在，且不是 SDD 安全模型的实现。

**验证：** 权限与审批在文档中是两套控制；高风险操作不再只挂 G6；未实现机制均标注。

### P0-002-06 平台清单与兼容性声明

**修改前：** 平台目录树缺少 OpenClaw；多个平台的 ✅ 状态没有实测证据；OpenClaw 被描述为“支持所有 SDD 特性”。

**修改后：**

- [platform-architecture.md](../architecture/platform-architecture.md) 统一六个平台：Codex、Claude Code、Cursor、Gemini CLI、OpenCode、OpenClaw。
- 平台目录规划包含 `platforms/openclaw/`，六个平台均规划 `skill-metadata.yaml`。
- 能力矩阵改为**设计假设矩阵**，图例区分预期原生/预期适配/预期不支持/未评估/未验证。
- 单独列出 OpenClaw 已实测能力（仅 CLI 会话投递/读取、health/status、skills list）及证据范围，明确不能推断 SDD 全部特性。
- [ADR-004](../decisions/ADR-004-cross-platform.md) 同步更新矩阵、目录和未验证声明。
- [system-architecture.md](../architecture/system-architecture.md)、README、P0 交付报告、风险清单统一六平台清单。

**验证：** 六平台清单在所有相关文档一致；未实测能力不再写 ✅ 或“支持所有 SDD 特性”。

### P0-002-07 Task Context 与 Artifact 管理

**修改前：** ADR-005 只有产物目录草图，缺少 task-id 创建者、状态维护、归属、写入权限、并发、版本和归档规则；`platform-config` 与平台配置内容混用。

**修改后：**

- [ADR-005](../decisions/ADR-005-task-context.md) 成为 Task Context / Artifact 的唯一权威定义：
  - Task Context 字段：task-id、project-root、task-type、complexity、task-status、current-stage、user-preferences、platform-config（引用）、task-constraints、artifact-references。
  - 状态机：created → planned → executing → awaiting_approval → verifying → completed / failed / aborted。
  - Artifact 字段：id、path、type、stage、created_by、created_at、source、version、sha256、status、references。
  - 写入：单写者、任务级/路径级锁、原子写入、禁止静默覆盖、冲突生成新版本。
  - 隔离：任务命名空间；跨任务引用必须显式（路径+版本+hash）。
  - 归档：完成后冻结，按保留策略归档，删除需审批。
- [module-architecture.md](../architecture/module-architecture.md) 改为引用 ADR-005，不再重复定义产物结构。
- [security-architecture.md](../architecture/security-architecture.md) 的只读共享、写入隔离、权限边界与 ADR-005 对齐。

**验证：** `platform-config` 只作为引用；并发写入、版本、归档都有明确规则；安全文档与 ADR-005 不冲突。
